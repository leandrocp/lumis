A parser is a dependency. You add it, your package manager pins it, and it is
there — or you did not add it, and it is not.

That is worth saying because it used to be otherwise. Highlighting resolved
parsers on demand and kept whichever compatible version a machine downloaded
first, so two machines could render the same document differently and nothing
recorded which parser produced which output. Declaring them removes the
question: the set is in a file you already review, pinned by a lock you already
have.

## One rule, one place to look

Every runtime resolves parsers the same way: **only the ones the project
installed**, with no fallback that fetches anything else. A parser is a
dependency, declared where that runtime's dependencies already live.

| Runtime | Declares its parsers in | Pinned by |
| --- | --- | --- |
| Rust | `Cargo.toml` features | `Cargo.lock` |
| JavaScript / TypeScript | `package.json` dependencies | your package manager's lockfile |
| Elixir | `mix.exs` dependencies | `mix.lock` |
| CLI | nothing | — |

Rust links parsers statically. JavaScript installs `@lumis-sh/wasm-*`. Elixir
depends on `lumis_wasm_*`, whose `priv/parsers` holds the bytes — so they travel
into a release like any other dependency's assets, with no data directory to
prepare and nothing to copy.

The CLI is the exception, deliberately. It has no project and downloads what it
needs, because a viewer is not the application whose output a declaration
governs, and a highlighter that behaved differently depending on the directory
you ran it in would be worse than one that does not.

  <Tab value="Elixir">

Add the parsers you want to `mix.exs`. There are no Lumis-specific commands:
`mix deps.get`, `mix deps.update` and `mix.lock` already are them.

```elixir title="mix.exs"
defp deps do
  [
    {:lumis, "~> 0.8"},
    {:lumis_wasm_rust, "~> 0.26"},
    {:lumis_wasm_bundle_web, "~> 0.26"}
  ]
end
```

A bundle is a package whose dependencies are its members, so it widens when it
gains a language and `mix deps.update` picks that up — a visible `mix.lock`
diff, not a silent change.

```bash title="Move a pinned version"
mix deps.update lumis_wasm_rust
```

```bash title="Stop using it"
# remove the line from mix.exs, then
mix deps.unlock --unused
```

A project that vendors parsers rather than depending on them can point at the
directories instead. Same layout, same verification; only how they got there
differs.

```elixir title="config/config.exs"
config :lumis, parser_dirs: ["priv/parsers"]
```

  </Tab>
  <Tab value="JavaScript / TypeScript">

Install the parsers you want. Your package manager's lockfile pins them, so
there is no separate Lumis lock.

```bash
npm install @lumis-sh/wasm-rust @lumis-sh/wasm-json
```

Rust and JSON now highlight. A Markdown file with a Haskell block renders that
block as plain text — Lumis will not go and fetch `haskell`.

Install nothing and nothing highlights. There is no fallback that fetches a
language the project did not install, the same way Rust cannot use a language
that was not compiled in. Install `@lumis-sh/wasm-bundle-full` to get them all.

A bundle installs a set in one package:

```bash
npm install @lumis-sh/wasm-bundle-web
```

Parsers are read out of `node_modules` — the manifest through each package's
`./lumis.json` export — so nothing is fetched at runtime.

Supplying your own resolver is a declaration too, and takes precedence: a
caller that said where parsers come from has answered the question the
dependency list otherwise answers.

Nothing is fetched at runtime.

```toml title="Cargo.toml"
lumis = { version = "0.13", default-features = false, features = ["lang-rust", "lang-elixir"] }
```

## What a language you did not add does

Naming a language explicitly is your decision, so one you never depended on is
an error rather than a silent download:

```elixir
Lumis.Languages.load("haskell")
#=> {:error, :not_installed}
```

A language an *injection* names is content rather than a decision — a fenced
block in a README, say — so that block renders plain and the document is fine.
A missing parser costs one block, not the page.

## Releases

Nothing to prepare. Parsers are dependencies, so `mix release` carries them the
way it carries any dependency's `priv/`:

```
_build/prod/rel/my_app/lib/lumis_wasm_elixir-0.26.3/priv/parsers/
  elixir.lumis.json
  tree-sitter-elixir-0.26.3-....wasm
```

The released node reads them from there. There is no data directory to stage, no
copy step, and no network at boot or at render time.

`config :lumis, :data_dir` still has a job, a smaller one: it holds the compiled
WASM module cache, which is a speed-up rather than a source. Point it somewhere
writable and persistent and a restart skips recompiling; lose it and the first
render of each language is slower and nothing else changes.

## Verification

Bytes that arrive through a package manager have a checksum behind them already,
and Lumis checks them again anyway. Each parser is verified against the
`lumis.json` shipped beside it, and a package outside the Tree-sitter series
this Lumis speaks is refused rather than loaded. A corrupt file in a dependency
fails at load instead of reaching the runtime.
