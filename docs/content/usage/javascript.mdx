Use the same `@lumis-sh/lumis` package in JavaScript and TypeScript projects.
Its exports include TypeScript declarations; both use the same runtime on each host.

To highlight TypeScript source, import `@lumis-sh/lumis/langs/typescript` or
`@lumis-sh/lumis/langs/tsx`. The language you highlight is independent of
whether your app uses JavaScript or TypeScript.


## For one-off highlighting

Use [`highlight()`](https://www.npmjs.com/package/@lumis-sh/lumis) when you just need one async highlight call and do not need to keep a highlighter instance around.

```ts
import { highlight } from "@lumis-sh/lumis";
import { htmlInline } from "@lumis-sh/lumis/formatters";
import javascript from "@lumis-sh/lumis/langs/javascript";
import frappe from "@lumis-sh/themes/catppuccin_frappe";

const html: string = await highlight(
  "const x = 1",
  htmlInline({ language: javascript, theme: frappe }),
);
```

`highlight()` uses a shared default runtime, so loaded languages and global WASM resolver changes are process-wide.

## For reusable highlighters

Use [`createHighlighter()`](https://www.npmjs.com/package/@lumis-sh/lumis) when you want instance isolation, explicit setup, lazy loading, or repeated synchronous `hl.highlight()` calls after initialization.

```ts
import { createHighlighter } from "@lumis-sh/lumis";
import { htmlInline } from "@lumis-sh/lumis/formatters";
import javascript from "@lumis-sh/lumis/langs/javascript";
import frappe from "@lumis-sh/themes/catppuccin_frappe";

const hl = await createHighlighter({
  languages: [javascript],
});

const html = hl.highlight(
  "const x = 1",
  htmlInline({ language: javascript, theme: frappe }),
);
```

This creates an isolated highlighter unless you intentionally rely on the global resolver.

## Bundles

Bundles register many languages lazily.

| Bundle                              | Purpose                                                                                     |
| ----------------------------------- | ------------------------------------------------------------------------------------------- |
| `@lumis-sh/lumis/bundles/web`       | HTML, CSS, JS, TS, JSON, Markdown, SQL, Svelte, Vue, Astro, and other web-focused languages |
| `@lumis-sh/lumis/bundles/web-extra` | framework and template languages that complement the web bundle                             |
| `@lumis-sh/lumis/bundles/system`    | C, C++, Rust, Go, Zig, LLVM, Make, CMake, and related system languages                      |
| `@lumis-sh/lumis/bundles/backend`   | popular backend languages plus common API, config, and infra formats                        |
| `@lumis-sh/lumis/bundles/full`      | all supported languages                                                                     |

```ts
import { createHighlighter } from "@lumis-sh/lumis";
import {
  bundledLanguages,
} from "@lumis-sh/lumis/bundles/web";

const hl = await createHighlighter({
  languages: [bundledLanguages],
});

// registered, including lazy entries
hl.registeredLanguages;

// loaded right now, usually just plaintext at first
hl.languages;
```

## Lazy loading

You can register a language now and load it only when needed.

```ts
import { createHighlighter } from "@lumis-sh/lumis";
import { htmlInline } from "@lumis-sh/lumis/formatters";
import {
  bundledLanguages,
} from "@lumis-sh/lumis/bundles/web";
import frappe from "@lumis-sh/themes/catppuccin_frappe";

const hl = await createHighlighter({
  languages: [bundledLanguages],
});

await hl.loadLanguage(bundledLanguages.javascript);

const html = hl.highlight(
  "const x = 1",
  htmlInline({
    language: bundledLanguages.javascript,
    theme: frappe,
  }),
);
```

`createHighlighter({ languages })` accepts:

- eager `Language` objects
- a bundle object
- dynamic import promises
- lazy import functions

## Repeated highlighting

Load languages once with `createHighlighter()`, then call `hl.highlight()` synchronously for repeated work.

```ts
import { createHighlighter } from "@lumis-sh/lumis";
import { htmlInline } from "@lumis-sh/lumis/formatters";
import javascript from "@lumis-sh/lumis/langs/javascript";
import frappe from "@lumis-sh/themes/catppuccin_frappe";

const hl = await createHighlighter({
  languages: [javascript],
});

const html = hl.highlight(
  "const x = 1",
  htmlInline({ language: javascript, theme: frappe }),
);
```

## Language references

These are equivalent at highlight time:

```ts
htmlInline({ language: json, theme });
htmlInline({ language: bundledLanguages.json, theme });
htmlInline({ language: "json", theme });
```

## Auto-detection and plaintext fallback

If you omit `language`, Lumis tries to detect it and falls back to plaintext when it can't.

Detection methods:

- file extensions (`.rs`, `.js`, `.ex`)
- filenames (`Makefile`, `Dockerfile`)
- shebangs (`#!/usr/bin/env python`)
- Emacs mode lines

```ts
const html = await highlight(
  source,
  htmlInline({ theme: frappe }),
);
```

Useful when rendering user-provided content or pasted snippets.

## Runtime notes

- every runtime loads the same per-language parser WASM; what differs is the engine that runs it
- on Node, `@lumis-sh/lumis` runs those parsers and the highlighting walk under Wasmtime in the same Rust code as the Lumis CLI and Elixir bindings; built-in formatters normally render there too, while custom formatters assemble events in JavaScript and an async call that may need a JavaScript resolver stays on the main thread
- browsers, and any platform with no prebuilt addon, run them under the host's own WebAssembly through `web-tree-sitter`, and walk and format in JavaScript
- the addon is prebuilt for macOS arm64 and x64, Linux arm64 and x64 against both glibc and musl, and Windows arm64 and x64; npm installs the one matching the host, so Alpine and other musl images get the same runtime as a glibc host
- `runtimeKind()` returns `'native'` or `'wasm'` if you need to confirm which one an install resolved
- the addon carries no parsers and loads each from the `@lumis-sh/wasm-*` package the project installed, so it costs about 4.7 MB of download on top of the Wasm runtime rather than one binary per language
- the package uses conditional exports so Node and web-standard runtimes get the right entry point automatically
- every language package contains matching queries plus an exact parser version, size, and SHA-256 digest
- Node keeps compiled parser modules, and anything a custom resolver fetched, in the platform user data directory; `LUMIS_DATA_DIR` overrides it
- browsers persist package metadata and verified parser bytes in CacheStorage with an IndexedDB fallback
- Node loads installed parser packages such as `@lumis-sh/wasm-elixir` or bundle packages such as `@lumis-sh/wasm-bundle-web`, and nothing else unless you configure a resolver
- ordinary Node highlighters share one Wasmtime runtime; a highlighter that supplies parser bytes, queries, or resolver callbacks gets an isolated Tree-sitter Wasm store so its definitions are released with that highlighter, while the Wasmtime engine and persistent caches remain shared
- non-Node usage usually relies on remote parser assets unless you override the resolver, use `withWasm()` with a single npm parser package such as `@lumis-sh/wasm-json`, or use `withWasmBundle()` with a bundle package such as `@lumis-sh/wasm-bundle-web`
- Bun and Deno are also supported

## Where parsers come from

Every language is a package. `@lumis-sh/wasm-rust` holds the Rust parser, the
queries written for it, and the parser's size and SHA-256 digest. The language
you import, such as `@lumis-sh/lumis/langs/rust`, only names that package. A
parser and its queries are released and tested together, so Lumis never pairs a
parser with queries from another release, and it refuses parser bytes that don't
match the digest.

  <Tab value="Node">

Install the parsers you highlight, one at a time or as a bundle:

```bash
npm install @lumis-sh/wasm-elixir
npm install @lumis-sh/wasm-bundle-web
```

Then import languages as usual. Lumis reads each parser out of its package in
`node_modules` and downloads nothing:

```ts
import { createHighlighter } from "@lumis-sh/lumis";
import elixir from "@lumis-sh/lumis/langs/elixir";

const hl = await createHighlighter({ languages: [elixir] });
```

A bundle package matches the Lumis bundle of the same name, so
`@lumis-sh/wasm-bundle-web` covers every language in
`@lumis-sh/lumis/bundles/web`. A language whose package the project didn't
install is refused, and so is an installed package that is too old to ship a
`lumis.json` or outside the supported version range. Update it in that case.
[Declaring parsers](/advanced/lock) explains why.

A browser has no `node_modules` to read, so by default Lumis fetches parsers
from jsDelivr, falling back to unpkg. It asks for the package metadata first,
then for the exact parser version the metadata names:

```text
https://cdn.jsdelivr.net/npm/@lumis-sh/wasm-<name>@0.26/lumis.json
https://cdn.jsdelivr.net/npm/@lumis-sh/wasm-<name>@<version>/<parser>.wasm
```

Verified bytes are kept in CacheStorage, or IndexedDB on WebKit, so a reload
doesn't fetch them again.

To ship parsers with your app instead, import them from npm and let your bundler
handle the files. `withWasm()` attaches one parser to its language:

```ts
import { createHighlighter, withWasm } from "@lumis-sh/lumis";
import elixir from "@lumis-sh/lumis/langs/elixir";
import elixirWasm from "@lumis-sh/wasm-elixir";

const hl = await createHighlighter({
  languages: [withWasm(elixir, elixirWasm)],
});
```

`withWasmBundle()` does the same for a whole bundle:

```ts
import { createHighlighter, withWasmBundle } from "@lumis-sh/lumis";
import { bundledLanguages } from "@lumis-sh/lumis/bundles/web";
import { bundledWasms } from "@lumis-sh/wasm-bundle-web";

const languages = withWasmBundle(bundledLanguages, bundledWasms);
const hl = await createHighlighter({ languages: [languages] });

await hl.loadLanguage(languages.javascript);
```

Both change only where the bytes come from. They still have to match the
package's digest.

## Custom resolvers

A resolver tells Lumis where to find package metadata and parser files, such as
your own CDN or a directory you serve. Configuring one is a declaration of its
own, so on Node it takes precedence over the installed packages.

```ts title="Every highlighter"
import {
  configureLanguagePackageResolver,
  configureWasmResolver,
} from "@lumis-sh/lumis";

configureLanguagePackageResolver(
  (packageName, versionRange) =>
    `https://unpkg.com/${packageName}@${versionRange}/lumis.json`,
);

configureWasmResolver(
  (_language, wasm) =>
    `https://unpkg.com/${wasm.packageName}@${wasm.version}/${wasm.name}.wasm`,
);
```

```ts title="One highlighter"
import { createHighlighter } from "@lumis-sh/lumis";
import rust from "@lumis-sh/lumis/langs/rust";

const hl = await createHighlighter({
  languages: [rust],
  languagePackageResolver: (packageName) =>
    `/wasm/${encodeURIComponent(packageName)}/lumis.json`,
  wasmResolver: (_language, wasm) => `/wasm/${wasm.name}.wasm`,
});
```

Whatever a resolver returns is still checked against the package's digest. On
Node, resolvers also answer for languages found inside a document; the next
section covers what that walk can read.

## Injected languages

On Node, highlighting loads a language injected inside a document during the
same pass that finds it, so a Markdown file with a fenced Rust block highlights
that block without Rust being named anywhere in your code. It loads from the
installed package, so install the languages a document can inject too. One that
isn't installed leaves its own block plain rather than failing the document, and
Lumis warns once naming it.

Configured [`configureLanguagePackageResolver()` and
`configureWasmResolver()`](#custom-resolvers) callbacks
participate in that same Node native path. They apply to a language first
discovered mid-document as well as to the root language, without a preload or
second pass.

The native walk has to read a newly discovered resolver result synchronously.
Local paths plus `file:`, `data:`, `http:`, and `https:` URLs work there. A URL
owned by JavaScript itself, such as a `blob:` URL, cannot be opened from Rust;
include that language in `createHighlighter({languages: [...]})` or call
`loadLanguage()` first so JavaScript resolves it before the synchronous walk.

In a browser, one-pass loading does not happen: loading is asynchronous there
and cannot run inside a synchronous walk, so load every participating language
yourself:

```ts
const hl = await createHighlighter({
  languages: [html, css, javascript],
});

const htmlOutput = hl.highlight(
  source,
  htmlInline({ language: html, theme: frappe }),
);
```

Languages from a bundle, including one with parser bytes from
`@lumis-sh/wasm-bundle-web`, are registered but not loaded. Call
`hl.loadLanguage()` for each one the document uses before highlighting it.

See [On demand](/languages#on-demand).

## Preload languages during application startup

Highlighting loads on demand, so preloading only decides *when* a language is
paid for. See [Languages](/languages).

Start serving, then load in the background:

```ts title="bootstrap.ts"
import { loadLanguages } from "@lumis-sh/lumis";

await startServer();

// Not awaited, so a slow compile delays no request. The
// `.catch()` is required: an unhandled rejection
// terminates the process.
loadLanguages(["javascript", "html", "css"]).catch(
  (error) => {
    logger.warn(
      { error },
      "Lumis preload failed; languages load on demand",
    );
  },
);
```

`loadLanguages()` warms the same default runtime `highlight()` uses, so nothing
has to be threaded through the application. `createHighlighter({languages})` is
the same load into an instance you keep yourself.

Awaiting a preload before `startServer()` puts every compile on the boot path,
so the process accepts no request until the slowest one finishes.

The API accepts `bundle-*` names such as `bundle-web`, covering the same
languages as the matching `@lumis-sh/wasm-bundle-*` package. Each parser is
checked against its package's size and SHA-256 before it loads.

When the native Node addon is available, the API also validates each parser and
its queries and persists the compiled Wasmtime module in the data directory.
The portable fallback can't: `web-tree-sitter` does not persist its compilation
across processes.

To compile in an image build or a prestart step instead, run the same
`loadLanguages()` there and await it, with `LUMIS_DATA_DIR` pointing at the
directory the server will use. The server then reuses those compiled modules.
Being a separate process is the point: failing there fails the build rather than
a request. [Languages](/languages#preloaded) has the command, and why
`lumis languages download` is not the build step for a Node project.

:::note Edge is not supported yet
The portable JavaScript runtime uses `web-tree-sitter`, but Edge runtimes are not supported yet because of an upstream Tree-sitter limitation: [tree-sitter/tree-sitter#2160](https://github.com/tree-sitter/tree-sitter/issues/2160).
:::
