A language in Lumis is a Tree-sitter parser: a WebAssembly module that Lumis
verifies, compiles, and loads. You have two ways to get one, and you can use
both.

|  | On demand | Preloaded |
| --- | --- | --- |
| What you write | nothing | a list of languages, once |
| First document in a language | pays the compile | already loaded |
| Every document after | full speed | full speed |
| A language you did not expect | works | works, on demand |

**On demand is the default and needs no setup.** Highlight a document and Lumis
loads whatever that document turns out to name. **Preloading is the same work,
moved off your users' first request** — it is the "pick a language" step done
ahead of time instead of during a request.

Both end in the same place. Preloading only decides *when* you pay.

## On demand

Nothing to declare. Lumis resolves, verifies, and loads a language the first
time a document names it, then reuses it for every later document.

Where the bytes come from depends on the runtime. In Elixir and Node a parser is
an ordinary dependency: `mix deps.get` and `npm install` deliver it, and
highlighting reads it off the code path without touching the network. The CLI
has no manifest to read, so it downloads and verifies a parser the first time it
needs one. Browsers fetch theirs and keep them in CacheStorage.

That includes languages **injected inside** another one, in the same pass: a
Markdown file with a fenced Rust block highlights that block, and an HTML page
highlights its `<style>` and `<script>` contents, without any of them appearing
in your code.

A language that cannot be loaded costs its own block, not the document. A
thousand-line file still highlights when one fenced block names something the
project never installed; that block stays plain.

The cost is a Wasmtime compile: seven parsers take about 8 s to compile, against
1.3 s once their compiled forms are stored. Registering an already-compiled
parser is 3-15 ms, and about 0.3 ms after that. So the penalty is real but it is
paid once per language, by whichever request arrives first.

That is fine for a CLI, a script, a build step, or anything where one slow first
render does not matter. Preload when it does.

:::note
Browsers are the exception. `web-tree-sitter` loads asynchronously, so a parser
cannot be loaded inside a synchronous walk: in a browser, preload an injected
language before highlighting the document that mentions it, or use a bundle.
Node does not have this limit — it highlights through a native addon.
:::

## Preloaded

Name the languages you want. Which call depends on whether the process doing
the work is the one that will serve:

| Runtime | In the process that serves | In a process that exits |
| --- | --- | --- |
| JavaScript / TypeScript | `loadLanguages([...])`, not awaited | `lumis languages download <names>` |
| Elixir | `Lumis.Languages.async_load([...])` in `start/2` | `lumis languages download <names>` |
| Browsers / CDN | `createHighlighter({languages})`, or `loadLanguages()` | — nothing to prepare ahead |
| CLI | — the process exits, so there is no later to hold for | `lumis languages download <names>` |
| Rust | — parsers are Cargo features compiled into the binary | — |
| Java | construct `Lumis` at startup and retain it | — parsers ship inside `lumis4j` |

**Loading** compiles the language and keeps it in this runtime, so nothing
compiles it again, and it persists the compiled module on disk, where it
survives restarts and is shared by every native runtime pointed at the same
directory.

A process that will serve loads. A process that is *not* serving — an image
build, a release task — has nothing to hold on to, so it runs the CLI, which
writes that same directory and exits.

:::note
Preloading is an optimization, never a prerequisite. An application that starts
cold serves correctly the whole time it is loading, so preloading must never
delay a boot or fail one — every example below keeps both true.
:::

### Which languages to name

Name your root languages and anything they can inject. Markdown may need the
languages used in fenced code blocks, and HTML may inject CSS and JavaScript.
Prefer a focused list or a small bundle. Anything you miss still loads on
demand.

### Why `bundle-full` is not the safe default

Every language a process loads shares one Tree-sitter Wasm store, and that
store's memory is capped at 128 MB. Each parser adds its static data to it and
nothing is ever reclaimed, so the limit is the *total* of everything loaded,
not a count and not a per-parser size.

The published parsers now come close enough to that ceiling that loading all of
them can fail — and the failure lands on whichever languages happen to be asked
for last, so the set that breaks changes between runs. Name the languages you
serve, or take `bundle-web`, `bundle-system` or `bundle-backend`, which are
sized for this.

`bundle-full` excludes **SystemVerilog**. Its parse tables are 22 MB, 17% of
that 128 MB budget and around 200x the median parser, and with it the bundle
does not fit at all. It is still a language like any other: install it and name
`systemverilog` and it loads.

Installing it does not make preloading everything safe, though. Installing is a
dependency; loading is what spends the budget. Even without SystemVerilog the
published set leaves only a few MB spare, so preload the languages you actually
serve and leave the rest to load on demand — a language nobody asks for costs
nothing.

[Language catalog](/reference/languages) has every name, and the package each
one resolves to.

All of these operations are safe to repeat. A normal run reuses valid files;
the CLI's `--force` is an explicit update that resolves the compatible package
range again.

## Preloading, per runtime

<Tabs groupId="runtime" persist items={['JavaScript / TypeScript', 'Elixir', 'CLI', 'Browsers / CDN', 'Rust', 'Java']}>
  <Tab value="JavaScript / TypeScript">

Start serving, then load in the background:

```ts title="bootstrap.ts"
import { loadLanguages } from "@lumis-sh/lumis";

await startServer();

// Not awaited, so a slow compile delays no request. The
// `.catch()` is required: an unhandled rejection
// terminates the process, which is exactly the failure
// loading in the background is meant to avoid.
loadLanguages(["javascript", "html", "css"]).catch(
  (error) => {
    logger.warn(
      { error },
      "Lumis preload failed; languages load on demand",
    );
  },
);
```

`loadLanguages()` warms the same default runtime the module-level `highlight()`
uses, so nothing has to be threaded through your application. It accepts catalog
names, aliases, and bundle names such as `bundle-web`. Every name is attempted;
if any fail it rejects with an `AggregateError` naming each one, after the rest
have loaded.

`createHighlighter({languages})` is the same load into an instance you keep
yourself, and is what browsers use.

On the native Node addon, loading validates the parser and queries and persists
the compiled Wasmtime module. Bun and Deno, or a Node installation without the
addon, call the same API, but the portable `web-tree-sitter` fallback cannot
persist compiled modules across processes.

Use the CLI tab below when a build or prestart step is preparing a directory the
serving process will read.

  </Tab>
  <Tab value="Elixir">

Call `Lumis.Languages.async_load/1` from your application's `start/2`:

```elixir title="lib/my_app/application.ex"
def start(_type, _args) do
  Lumis.Languages.async_load([
    "markdown",
    "elixir",
    "javascript"
  ])

  Supervisor.start_link(children(),
    strategy: :one_for_one,
    name: MyApp.Supervisor
  )
end
```

It returns before the compile starts, so the boot never waits on it. The return
value is deliberately not matched: the work runs under a `:temporary` child of
Lumis's own supervisor, so a failure is logged and never retried, never
escalates, and cannot stop the application from starting.

The API accepts language names and `:bundle_*` names such as `:bundle_web`.

Loading is global to the VM: one `Runtime` lives in the NIF, so the first
process to need a language pays and every process after it does not.

Use `Lumis.Languages.load/1` when the caller does want the result and can wait
— a release task, or a smoke test that should fail if a parser is unusable.
For release and container details, see the standalone
[Elixir deployment guide](https://lumis.hexdocs.pm/deployment.html).

  </Tab>
  <Tab value="CLI">

Use the CLI when preparation belongs outside the application lifecycle: an image
build, a release task, or an operations step. It fills the store for a process
that has not started yet, which is the case a startup preload cannot cover.

```bash
lumis languages download rust javascript elixir
lumis languages download bundle-web
lumis languages download --all
```

Refresh compatible versions already in the store with `--force`:

```bash
lumis languages download rust javascript --force
```

For an image build, name the destination explicitly and copy that same
directory into the runtime image:

```dockerfile
FROM node:22-bookworm-slim AS parsers
RUN npx --yes @lumis-sh/cli --data-dir /app/lumis \
      languages download markdown elixir javascript

FROM debian:bookworm-slim
COPY --from=parsers --chown=nobody:root \
  /app/lumis /app/lumis
ENV LUMIS_DATA_DIR=/app/lumis
```

The first stage only needs a Node image because `npx` fetches the CLI; nothing
from it reaches the runtime image except the directory. Install the binary
instead — see [Installation](/installation) — if you would rather not reach the
network during a build.

Keep the startup preload as well. A prepared directory removes the compile;
moving the parsers into the runtime is still the preload's job, and it needs no
network once that directory is there.

  </Tab>
  <Tab value="Browsers / CDN">

`loadLanguages()` works here too, warming the runtime the module-level
`highlight()` uses. When you keep a highlighter instead, load into it and retain
that instance:

```ts
import { createHighlighter } from "@lumis-sh/lumis";
import css from "@lumis-sh/lumis/langs/css";
import html from "@lumis-sh/lumis/langs/html";
import javascript from "@lumis-sh/lumis/langs/javascript";

const highlighter = await createHighlighter({
  languages: [html, css, javascript],
});

await renderApplication({ highlighter });
```

Pass eager language imports when they must be ready immediately. A bundle
registers lazy entries; call `highlighter.loadLanguage()` for the bundle members
the application must have.

Verified parser bytes persist in CacheStorage, with an IndexedDB fallback for
WebKit, but never a compiled module: WebAssembly compilation belongs to the
browser and cannot be persisted by Lumis. Browsers do not use `LUMIS_DATA_DIR`.

  </Tab>
  <Tab value="Rust">

The Rust crate has no parser download or runtime compilation step, so there is
no on-demand mode and nothing to preload. Select the languages at build time
with Cargo features; their parser code is compiled into the application:

```toml title="Cargo.toml"
[dependencies.lumis]
version = "0.1"
default-features = false
features = ["bundle-web", "lang-rust"]
```

There is no preload command, parser data-directory environment variable, or
runtime parser-cache configuration for the Rust crate.

  </Tab>
  <Tab value="Java">

`lumis4j` ships its Lumis WebAssembly module and languages with the Java
artifact, so there is nothing to download. Construct the `Lumis` instance during
application startup and retain it for the application lifecycle, so module
initialization happens before the first request:

```java
import io.roastedroot.lumis4j.core.Lumis;

var lumis = Lumis.builder().build();
startServer(lumis);

// Call lumis.close() from the application's
// shutdown lifecycle.
```

There is no parser cache command, `LUMIS_DATA_DIR`, or parser-store
configuration in `lumis4j`.

  </Tab>
</Tabs>

## Point every process at one directory

The CLI, Elixir NIF, and native Node addon share one store, so a parser one of
them compiles is already compiled for the others. Name it explicitly when one
process prepares files for another:

| Host | Explicit setting | Environment fallback | Default |
| --- | --- | --- | --- |
| CLI | `--data-dir /app/lumis` | `LUMIS_DATA_DIR` | platform user data directory |
| JavaScript / TypeScript | — | `LUMIS_DATA_DIR` | platform user data directory |
| Elixir | `config :lumis, data_dir: "/app/lumis"` | `LUMIS_DATA_DIR` | the Lumis application `priv/lumis` directory |

Elixir configuration takes precedence over the environment. Set `LUMIS_DATA_DIR`
for the deployed highlighter when it must read a directory a build step
prepared.

[WASM and CDN](/advanced/wasm-and-cdn#the-store-directory) has the directory
layout, integrity checks, custom resolvers, and offline images.
