# Stress test

This corpus reproduces input shapes that put the most pressure on Lumis. It is
intentionally separate from the normal test suite: full-size runs can take
minutes per render and allocate gigabytes. The same generated bytes are sent
through Rust, the CLI, Node's native addon, Node's `web-tree-sitter` fallback,
Chromium, and the Elixir NIF. Elixir also probes native work left running after
a caller times out.

The source files behind the first seed set were extracted from the latest
releases of 22,289 Hex.pm packages on 2026-09-20. Hex.pm is recorded as the
provenance of those individual origins; it is not the stress-test target. Their
contents were not copied into Lumis. Add future regressions from any Lumis
consumer or ecosystem to this same source-agnostic suite.

`corpus.json` describes ten synthetic cases covering 23 source files. A single
materialization step writes the input files and a manifest containing their
hashes; every runtime consumes those exact files. The cases retain the observed
language, byte count, line count, longest-line size, and structural depth of the
problematic inputs. They cover deeply nested JSON, minified single-line files,
bundled JavaScript, and large generated C++, Elixir, Erlang, Gleam, and CSV
sources.

No package source bytes are stored here. Package, version, path, SHA-256, and
shape measurements are factual provenance used to explain why each synthetic
case exists. See [LICENSES.md](LICENSES.md) for the copying decision.

## Run it

Run the full corpus through every runtime implemented in this repository:

```sh
mise run stress
```

Useful focused runs:

```sh
mise run stress -- --runtime rust --profile adversarial
mise run stress -- --runtime javascript-wasm --case deep-json --scale 0.001 --characterize
mise run stress -- --runtime elixir --profile adversarial --timeout-storm
```

The available runtime ids are `rust`, `cli`, `javascript-native`,
`javascript-wasm`, `browser`, and `elixir`. Java is maintained in the separate
`lumis4j` repository, so this suite cannot exercise it at all.

The `Stress test` workflow runs the same command on `workflow_dispatch` only,
because a full run is 18 jobs that are expected to exceed their budgets.

The lanes are deliberately redundant because the defect has not been localized:

- Rust exercises native Tree-sitter, the vendored `tree-sitter-highlight`
  implementation, Lumis, and its formatter directly.
- The CLI, Node native addon, and Elixir NIF exercise the Wasmtime parser path
  through three different host boundaries.
- Node Wasm and Chromium exercise `web-tree-sitter` in two JavaScript hosts.

A finding in one lane is not assigned to that host binding. Comparing the same
input and output hashes across lanes can narrow the responsible layer to a
parser or grammar, Tree-sitter error recovery, highlight queries and matching,
Lumis event composition or formatting, a parser runtime, or a host boundary.
More than one layer may contribute to the same end-to-end symptom.

Each runner checkpoints JSON after every case under
`target/stress-test/`, so a CI timeout or out-of-memory termination still
leaves the last completed measurement available for artifact upload. It records
wall time, source/output sizes, output hashes, output amplification, and the
memory counters available to that host. The Elixir lane additionally records
BEAM memory and the dirty-scheduler timeout probe. It builds the NIF in release
mode so its latency is comparable to the published runtime rather than to an
unoptimized development artifact.

The default budgets are deliberately stricter than the current behavior. A
full run fails when a render takes more than 30 seconds, output exceeds 32 times
the input, or a tiny probe waits more than five seconds after timed-out callers
have returned. `--characterize` records the same violations without making the
command fail.

Output determinism needs something to compare against, so `deterministic` is
`null` at the default `--iterations 1` and only `false` is a violation. Pass
`--iterations 2` to check it, as the workflow does.

## Baseline finding

One release-mode iteration of the 100,000-opening-bracket JSON case was measured
locally on Apple Silicon against the same Lumis core revision. Native Rust took
9.26 seconds, the CLI took 8.18 seconds, Node native took 8.18 seconds, Node
Wasm took 26.79 seconds, Chromium took 20.57 seconds, and the Elixir NIF took
8.19 seconds. Every lane produced the same 4,400,128-byte output under the same
SHA-256, which is 44.00128 times the 100,000-byte input.

This establishes an end-to-end problem below any single host binding while the
runtime spread also shows that the cost is not identical at every layer. These
measurements do not by themselves assign the time or amplification to the
grammar, parser, error recovery, highlight queries, event composition, or
formatter.

A separate concurrency check showed the operational failure: callers return
after their one-second timeout, but the native renders continue occupying dirty
CPU schedulers. The Elixir lane retains this host-specific probe, but it is one
symptom of the shared workload rather than the presumed root cause.

The five previously observed “diff line” failures were failures in Hex.pm's
large-match regular-expression extraction, not malformed Lumis HTML. They are
documented as integration evidence but are not asserted as Lumis defects here.
